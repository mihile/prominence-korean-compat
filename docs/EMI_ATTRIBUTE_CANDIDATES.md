# EMI search attribute candidate selection

Client build2026102706 preserves build2705 and narrows Custom Item Attributes' configuration traversal only during the synchronous EMI search bake. The measured search phase was4.89s. Its JFR samples frequently passed through attribute callbacks while generating tooltip text, including the already-existing ItemProperty lookup cache. The installed configuration contains106item definitions. A cached lookup still incurred a callback loop and cache queries for every unrelated definition at each slot/item tooltip.

Upstream references and installed-Fabric1.20.1/native comparisons are recorded in `SOURCE_REVIEW_WORKFLOW.md`. The CIA2.0.0 callback first matches an item's registry identity and only then applies NBT, slot rules and modifier creation. The independently authored patch selects matching definition objects before that unchanged native loop. It does not cache attribute values, modifier outputs, tooltips, equipment state or item stacks.

The candidate index belongs to one nested/thread-local EMI search-build scope and is dropped in finally. Only exact ArrayList sources containing exact native ItemProperty objects and fully valid IDs are supported. Each callback checks source identity/size/order, definition object identities and the mutable ID string references; a changed entry/list/order/ID rebuilds the index. Changes to attributes/slots/unbreakable fields are read by the original native code through the same objects. Duplicate matching entries keep their original order. Validation still scans definition references linearly; this is not advertised as an O(1) callback.

Empty/AIR/unregistered/custom stacks, unknown list/property shapes and malformed/null IDs retain the native full iterator. AIR matters because unknown configuration IDs resolve to the default item. A malformed ID is not thrown during preselection: the complete native loop retains earlier NBT/modifier updates and exception timing. Current item registry ID/binding is checked at each callback, and native SimpleRegistry/defaulted-registry class hashes are pinned. No normal gameplay/server callback is filtered outside the EMI build scope. The optional `attributeCandidates` guard also pins exact EMI1.1.24+1.20.1+fabric and CIA2.0.0 classes, Minecraft1.20.1 and MixinExtras0.5.4. Use `-Dprominence.emiHome.attributeCandidates=false` for a labeled diagnostic opt-out.

The earlier lookup/index wrappers remain active. `verify_attribute_native.py` runs real Mixin/MixinExtras transformations and ASM checks. Its baseline and candidate both have the previous property cache enabled. A headless fixture executes the native callback loop, NBT/slot checks and exception path using small platform/property/modifier probes. It compares output order/digest/NBT after definition mutation, duplicates, malformed input with partial updates and correction. Lookup-scope requests are60,600baseline versus1,200candidate with equal output. The original applyModifiers call sequence, including UUID/modifier creation, stays intact; the fixture uses a probe for modifier construction and is not actual game rendering or a complete attribute-system simulation.
