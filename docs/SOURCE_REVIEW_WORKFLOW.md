# Profiling-guided upstream source review

Use this sequence for later Minecraft performance work. Reuse valid evidence and these tools rather than redesigning captures for each change.

1. Read the installed JAR's Fabric metadata: mod ID/version/environment, Minecraft constraint, loader/API dependencies, source link and relevant class hashes. Then find the upstream release/tag/commit and its gradle.properties/fabric.mod.json. A branch named1.20.1 alone does not prove the installed version matches. Inspect Fabric/common code, not a Forge/NeoForge implementation with the same feature name.
2. Pin a complete Git commit for notes. Compare upstream control flow and descriptors against the installed native bytecode/mappings. Yarn and Mojang symbol names may differ. A source version mismatch is evidence to investigate, not permission to update other mods. Keep downloaded/decompiled code local where required; author a narrow compatibility patch instead of repackaging another mod's sources.
3. Select a concrete measured cost using both JFR and phase/plugin wall-clock logs. Samples are not exact elapsed-time percentages. Repeated allocation is not retained ownership. For a3-minute capture use the shared profiler, then heap/MAT; use retained heap/strong GC-root paths for memory ownership. Judge the target JVM's actual heap limit/after-GC usage. Machine-wide free RAM is not the user's primary metric.
4. Describe work removed and preserved outputs before implementation. Prefer reducing repeated traversal/lookup/construction within a valid scope. Check configuration, locale, registry/NBT/slot mutations, custom subclasses, malformed input, exception ordering, fallback, thread ownership, cancellation and reload invalidation. Do not make initialization appear fast by omitting items/recipes/tooltips/search, parallelizing arbitrary plugins sharing mutable registries, or accepting a stale disk cache without a complete invalidation key.
5. Check current upstream fixes/issues and existing local mixins before introducing another cache. Verify client/server scope and API compatibility. Exact versions/native fingerprints disable the optional patch on drift. Keep the latest cumulative compatibility JAR and canonical name/version; increment only the internal build.
6. Test native transformed methods with the existing local cache enabled for both baseline and candidate. Add targeted data fixtures for actual risks, preserve previous classes/helper/key, publish the reviewed signed cumulative GitHub release, and re-download/verify it. Distinguish publication, installation, guard activation, actual behavior and measured performance. Fixture operation reduction is never whole-game acceleration.
7. Compare a single combined update using a consistent label/route/settings and3-minute JFR/frame/GPU followed by a heap every time. Record whether first join, reconnect, first dimension visit or revisit; do not mix those as controlled A/B data. Reuse saved JFR/MAT to implement independent safe fixes before requesting another restart. Record unresolved candidates and limitations.

Use Minecraft's actual launcher metadata for shared runtime libraries as well as mod versions. Minecraft1.20.1 launches with Gson2.10; a newer Gson in a private build/test classpath can hide a startup NoSuchMethodError. Compile and run native fixtures with that runtime library first, and run `RuntimeGsonAbiTests` over the cumulative JAR. Optional Mixin guards must fail closed on dependency linkage errors. Build3006 exposed this gap; build3007 uses `JsonObject.size()` and verifies all44 referenced Gson members against2.10.
