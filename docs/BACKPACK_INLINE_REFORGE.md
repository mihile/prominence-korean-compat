# 배낭 모루 안에서 재단조

정교한 배낭의 모루 탭에서 **재단조**를 누르면 같은 오른쪽 패널이 재단조 모드로 바뀝니다. 장비를 위쪽 가운데 칸, 전용 재료와 첨가제를 양옆에 넣고 작은 단조 버튼을 누릅니다. 아래의 **모루로 돌아가기**로 일반 모루를 사용합니다. 배낭과 플레이어 보관함을 계속 볼 수 있습니다.

일반 모루 두 입력과 재단조 세 입력은 따로 보관합니다. 모드 전환·배낭 닫기 후에도 모루 업그레이드의 원래 `craftingInventory` NBT에 남습니다. 업그레이드를 버리거나 잃으면 그 안의 아이템도 함께 잃을 수 있으므로 보관 중인 아이템을 먼저 꺼내세요.

build2026102605부터 작은 단조 버튼에 마우스를 올리면 원래 Tierify 화면처럼 부족한 전용 재료 목록과 수리 필요 안내를 보여줍니다. 동기화된 재단조 데이터, 도구·방어구 수리 재료, 기본 재료 태그 순서로 조회하며 아이템의 현재 번역 이름을 사용합니다. 맞는 재료를 이미 넣었다면 원래 화면처럼 해당 부족 안내를 숨깁니다. 재료 소모나 재단조 규칙은 변경하지 않으며 클라이언트만 업데이트하면 됩니다.

멀티플레이에서는 **클라이언트와 서버 양쪽**에 대응 수정본이 필요합니다. 구형 상대와는 기존 세 슬롯 구성을 유지하고 버튼을 비활성화합니다. 양쪽이 지원을 확인한 뒤 여는 배낭만 여섯 슬롯을 등록합니다. 확인 직전에 배낭을 열었다면 한 번 다시 엽니다. 기존 별도 재단조 화면을 여는 버튼은 새 클라이언트에서 사용하지 않습니다.

클라이언트 build2026102603 / 서버 build2026102602에서 탭 전환 판정을 수정했습니다. Core의 서버 `isOpen` 값은 배낭 생성 시에만 초기화되어 이후 선택한 모루 탭과 달라질 수 있습니다. 이제 현재 배낭의 `getOpenContainer()`와 업그레이드 객체를 확인하여 전환·재료 슬롯·단조·준비 여부 갱신에 같은 기준을 사용합니다. 이전 배낭이나 닫힌 탭의 요청은 계속 거절합니다. 멀티플레이에서 이 오류를 고치려면 서버용 수정도 필요합니다.

`tools/verify_inline_selection.py`는 설치된 Core의 원래 선택/플래그 메서드 여섯 개를 데이터 전용 fixture에 넣고 실제 공개 JAR의 receiver와 InlineState를 실행합니다. `--baseline`은 이전 공개본에서 새로 연 모루의 전환 거절과 닫힌 탭의 오래된 true 플래그 문제를 재현합니다. 수정본은33검사로 전환·회신·입력 슬롯·단조·동일 틱 제한·다른 탭·접근 거부·구형 상대를 대조합니다. 실제 게임이나 월드는 실행하지 않습니다.

- `tools/verify_inline_native.py`는 실제 native7대상414메서드와 기존 모루 비용/재단조 탭 믹신을 함께 변환·ASM 검사합니다. Tierify의5개 판정·소모·종료 메서드 호출열이 보존됩니다. 데이터 전용 fixture는 실제 Porting handler/Fabric ItemVariant와 production InlineInventory를 사용해5칸 저장/재열기, NBT 보존, 분할·회수·비우기와 기존 모루 입력 보존을 검사합니다. 게임·월드·OpenGL은 시작하지 않습니다.

실제 배낭 GUI 조작과 멀티플레이 왕복 검수는 사용자 적용 후 확인할 항목입니다. 오프라인 변환·저장 검사를 실제 플레이 검수로 표시하지 않습니다.

추가 재료 안내 검사는 `tools/verify_inline_tooltip.py`를 사용합니다. 데이터 전용 native registry와 실제 Tierify ReforgeDataLoader로17검사(도구·방어구 수리 재료, 우선 지정 재료와 여러 대안, 같은 스택의 데이터 교체/초기화, 기본 태그, 올바른 재료/수리 경고/메타데이터 보존)를 실행하며 실제 게임·월드·OpenGL은 시작하지 않습니다.

## 2026-10-29: 석재 절단기 EMI 연결 (client nightly-20261029.2)

설치 Sophisticated Core1.2.7.15.166 / Backpacks3.23.4.5.110 / EMI1.1.24+1.20.1+fabric의 원래 `EmiGridMenuInfo.stonecutting()`은 등록돼 있지만 supportsRecipe가CRAFTING만 허용하고 craft도CRAFTING컨테이너를 찾는다. StonecutterUpgradeContainer는ICraftingContainer를 구현하지 않으므로 단순 category 수정으로는 부족하다.

기존 stonecutting 인스턴스에만 전용 handler를 연결한다. 열린 활성 석재 절단기를 우선하고 없으면 활성 업그레이드 중 슬롯 ID가 가장 낮은 것을 선택한다. 배낭/플레이어 보관함과 해당 입력 슬롯을 재료 소스로 쓴다. 실제 클라이언트 recipe manager에 ID가 존재하는지 확인한 뒤, 다른 열린 패널을 닫고 대상 패널을 연다. EMI clientFill의 일반 슬롯 클릭으로 재료를 옮기고, 갱신된 배낭 레시피 목록에서 정확한 ID를 찾아 native selectRecipe를 호출한다. 출력의 아이템/NBT/수량이 맞는지 확인한 뒤 요청한 CURSOR 또는INVENTORY동작을 보낸다. NONE은 선택된 상태로 남겨 둔다. 비동기 예약 클릭이나 사용자 인벤토리를 직접 만드는 코드는 없다.

네트워크는 기존 탭 전환/슬롯 클릭/배낭 레시피 선택 패킷만 사용한다. 서버용 호환 JAR 교체는 필요 없다. 원래 대장장이 패치와 새 믹신을 함께 실제 클래스에 변환해ASM으로 확인했다. 입력Slot.setChanged→레시피 갱신, selectRecipe→출력 갱신/서버 패킷, clientFill→정상 슬롯 클릭 연결도 native bytecode로 검증했다. 순서/실패 fixture는 실제 멀티플레이 검수를 대신하지 않는다. 꽉 찬 보관함에서 기존 입력 재료를 돌려놓을 공간이 없는 등 EMI 원래 clientFill의 제약은 유지된다.
