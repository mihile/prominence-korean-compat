차원 이동 중 Voxy의 LOD 데이터베이스를 열 때 발생한 파일 잠금 오류가 클라이언트 전체 종료로 전파되지 않도록 보완했습니다. 기존 통합 클라이언트 JAR 이름과 버전 `1.0.0`을 유지합니다.

<details>
<summary>변경 내용</summary>

- 검수한 Voxy 클라이언트 인스턴스에서만 RocksDB의 특정 LOCK 열기 오류를 처리합니다. 저장소 손상·디스크 부족·다른 불변식 오류는 숨기지 않습니다.
- 잠금 실패 후 프레임마다 다시 열지 않고250ms/1s/2s/4s/8s/16s 간격으로 최대7회 시도합니다. sleep이나 추가 저장소 작업 스레드는 없습니다. 정상적으로 열리면 원래 LOD 엔진·참조 수·저장 경로를 그대로 사용합니다.
- 렌더러, 로컬 청크 수집, 서버 LOD 수신/manifest 조회가 같은 상태를 확인합니다. 기존 수신기의 실패 응답·버퍼 해제 경로는 유지합니다. 재시도 동안 일반 지형과 셰이더를 유지하며 잠금을 강제로 풀지 않습니다.
- 계속 실패하면 해당 월드의 LOD 초기화를 잠시 중지하고 안내합니다. 차원을 다시 방문하거나 재접속하면 새 문맥에서 다시 시도합니다. 재시도 상태는 월드/인스턴스를 강하게 보관하지 않으며 인스턴스당 최대64항목입니다.
- Minecraft1.20.1, Voxy port.9와 RocksDB10.2.1의9개 native 클래스 지문에 맞을 때만 활성화합니다. 선택 비활성화는 `-Dprominence.voxyStorageRecovery=false`입니다.

서버 JAR·서버 설정, Voxy/VoxyServer JAR, 기존 LOD 파일·LOCK 파일, 개인 설정과 셰이더 옵션은 변경하지 않습니다.

</details>

<details>
<summary>원인과 검증 범위</summary>

실제 차원 왕복 중 Voxy 데이터베이스의 LOCK 열기 오류를 확인했습니다. 이전 DB는13초 전에 정상 종료됐다는 로그가 있어 단순한 닫기/열기 경합으로 단정하지 않습니다. 당시 잠금을 잡은 주체는 확정하지 못했습니다. 새 셰이더 텍스트 캐시 오류나 메모리 부족 예외는 이번 크래시의 직접 예외가 아닙니다.

설치된 native backend/JNI로 임시 데이터베이스40회 닫기/재열기, 실제 중복 열기 충돌, 잠금 해제 후 데이터 보존을 검증했습니다.46개 분류·재시도·한도·문맥 변경·동시성·약한 수명·지문·실제 DB 복구 검사와 기존 회귀 검사를 통과했습니다. 실제 Voxy/VoxyServer/WorldRenderer Mixin 변환3대상168메서드에서 원래 열기/잠금 해제/identifier 본문을 보존했습니다. 이전395클래스와 updater helper는 바이트 그대로입니다.

실제 게임/월드/OpenGL은 도구가 실행하지 않았습니다. 수정 후 실게임에서 같은 오류가 복구되는지는 다음 실행 검수입니다. 파일 잠금의 외부/내부 주체를 확인했다거나 첫 접속·차원 이동 렉 전체를 해결했다고 주장하지 않습니다.

</details>
